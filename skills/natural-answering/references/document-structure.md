# 문서 구조 (document-structure)

`~/llm-wiki-docs/` 밖에 만드는 문서에 쓴다. 위키 페이지는 `llm-wiki-docs` 스킬 규약을 따른다.

**어느 글이 프로젝트 문서이고 어느 글이 위키 페이지인가**는 `llm-wiki-docs` 스킬의 경계 절이
정본이다. 한 줄로 줄이면 이렇다:

> 코드가 바뀔 때 같이 바뀌어야 하는 글이면 프로젝트 문서, 코드가 바뀌어도 유효한 글이면 위키다.

프로젝트 문서를 요약해 위키 페이지를 만들지 않는다. 같은 사실이 두 곳에 살면 한쪽만 고쳐지고,
안 고쳐진 쪽이 더 그럴듯해 보인다.

모든 문서에 같은 목차를 강제하지 않는다. **공통 뼈대는 유지하고, 종류에 따라 세부를 바꾼다.**

## A. 공통 구조

| 순서 | 항목 | 포함할 내용 |
|---|---|---|
| 1 | Metadata | 제목, 버전, 작성·수정일, 상태 |
| 2 | Overview | 문서의 목적과 핵심 내용 요약 |
| 3 | Background | 배경, 문제 정의, 필요성 |
| 4 | Scope | 적용 범위와 제외 사항 |
| 5 | Main Content | 상세 설명, 구조, 기술적 내용 |
| 6 | Implementation / Usage | 구현 방식 또는 사용 방법 |
| 7 | Validation | 검증 방법과 확인된 결과 |
| 8 | Limitations | 제약사항, 알려진 문제 |
| 9 | References | 근거 문서, 공식 링크, 관련 코드 |
| 10 | Changelog | 문서 변경 이력 |

**관련 없는 항목은 생략한다.** 빈 제목만 남기는 것이 가장 나쁘다 — 채워진 문서로 보이지만
아무 내용이 없다.

## B. 종류별 구조

| 문서 종류 | 필수 구조 |
|---|---|
| README | 소개 → 주요 기능 → 요구사항 → 설치 → 설정 → 실행 → 테스트 → 문제 해결 |
| Architecture | 목적 → 시스템 구성 → 모듈별 역할 → 데이터 흐름 → 기술 스택 → 설계 결정 → 제약사항 |
| API Reference | Endpoint → 인증 → Parameters → Request → Response → Error → Example |
| Developer Guide | 개발 환경 → 프로젝트 구조 → 개발 규칙 → 실행 방법 → 테스트 → 배포 |
| Analysis Pipeline | 목적 → Input → Dependencies → Workflow → Parameters → Output → QC → Reproducibility |
| Troubleshooting | 증상 → 재현 조건 → 원인 → 해결 방법 → 확인 방법 → 재발 방지 |
| Research Report | 연구 목적 → 데이터 → Methods → Results → Discussion → Limitations → References |

## C. 문서를 쓸 때 지키는 일곱 가지

1. **문서 종류를 먼저 판별하고** 그 종류의 템플릿을 적용한다
2. 쓰기 전에 **기존 코드와 관련 문서를 확인한다** — 비슷한 문서가 이미 있으면 그것을 고친다
3. **코드나 공식 문서로 확인하지 않은 것을 사실로 쓰지 않는다**(`source-of-truth.md`)
4. **명령어·파일 경로·파라미터는 실제 구현과 대조한다.** 없는 API, 돌려 보지 않은 명령어가
   문서에 들어가는 것이 코드 관련 문서의 가장 흔한 사고다
5. 긴 문서에는 목차와 계층형 제목을 쓴다
6. 중복 설명을 줄이고, 관련 문서끼리 참조 관계를 유지한다
7. 다 쓴 뒤 **구조와 내용이 맞는지 확인한다** — 제목이 약속한 것이 그 아래에 실제로 있는지

4번은 기계로도 거른다: `scripts/check_prose.py --all` 이 문서에 적힌 파일 경로 가운데
실제로 없는 것을 `missing-path` 로 알려 준다. 다만 예시용 경로까지 같이 걸릴 수 있어
참고 등급이다 — 보고 판단한다.
