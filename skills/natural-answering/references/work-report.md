# 작업 보고 구조 (work-report-structure)

코드를 고친 뒤의 보고에 쓴다. 분석·실험 결과 보고는 이 구조가 아니라 `reporting.md` 쪽이다.

## 왜 이 형식인가

고친 과정을 길게 늘어놓고 자기평가("깔끔하게 처리했습니다")로 끝내는 보고가 있다.
그러면 읽는 사람이 정작 알아야 할 것을 직접 찾아내야 한다. 그 네 가지는 이렇다:

- 됐는지
- 무엇이 바뀌었는지
- 확인은 했는지
- 남은 위험은 무엇인지

순서를 고정해서 이 네 가지가 매번 같은 자리에 오게 한다.

## 표준 순서

| 순서 | 항목 | 내용 |
|---|---|---|
| 1 | 작업 결과 | 완료 / 부분 완료 / 실패 — 한 단어로 먼저 |
| 2 | 작업 요약 | 요청받은 것과 실제로 구현된 것 |
| 3 | 변경사항 | 바꾼 파일과 주요 구현 내용 |
| 4 | 검증 결과 | 테스트 · Lint · Type Check · Build 결과 |
| 5 | 문제 및 제약 | 미해결 문제, 위험 요소, 검증하지 않은 항목 |
| 6 | 후속 조치 | 실제로 필요한 추가 작업 |

## 지키는 규칙

- **1번이 맨 앞이다.** "완료"인지 "부분 완료"인지를 찾으려고 글을 읽게 하지 않는다
- **4번은 숫자로.** "테스트 통과"가 아니라 "단위 테스트 12/12 통과". 건너뛴 것과
  실패한 것은 그대로 쓴다(`finish-review` 2단계)
- **5번을 비우지 않는다.** 검증하지 않은 항목은 거의 항상 있다. "문제 없음"보다
  "무엇을 확인하지 않았다"가 언제나 더 정확하다
- **6번은 실제로 필요한 것만.** 해도 되는 일 목록이 아니다
- 작업 과정의 시행착오는 보고에 넣지 않는다. 단, **중간에 방법을 바꿨으면 왜 바꿨는지는 쓴다**

## 예시

```markdown
## 1. 작업 결과

완료

## 2. 작업 요약

사용자 인증 API에 JWT 인증과 토큰 만료 검증을 구현했습니다.

## 3. 변경사항

| 파일 | 변경 내용 |
|---|---|
| auth.py | JWT 검증 로직 구현 |
| config.py | 토큰 만료 설정 추가 |
| test_auth.py | 인증 테스트 추가 |

## 4. 검증 결과

- 단위 테스트 12/12 통과
- Lint · Type Check 통과
- 기존 인증 테스트 통과

## 5. 문제 및 제약

운영 환경에서의 토큰 갱신 동작은 검증하지 않았습니다.

## 6. 후속 조치

운영 환경과 같은 스테이징 환경에서 인증 통합 테스트가 필요합니다.
```

짧은 답변에서는 제목 대신 한 줄에 하나씩 써도 된다 — `작업 결과: 완료 — ...`, `작업 요약: ...`.
화면 하나(30줄) 안에 들어가야 하므로, 단계마다 한두 줄이면 충분하다.

`answer-check` 훅이 이 표를 직접 읽는다. 코드를 고친 턴의 마지막 답변에 여섯 항목이 이 이름과
이 순서로 있는지, 1번 바로 뒤에 결과 낱말이 있는지 본다. 이름을 바꾸려면 위 표를 고친다.

용어는 이 스킬의 규칙대로 처음 나오는 자리에서 푼다 — 위 예시의 `JWT`도 읽는 사람이
모를 수 있으면 `JWT(= 로그인 상태를 담은 서명된 쪽지)`처럼 한 줄을 붙인다.
