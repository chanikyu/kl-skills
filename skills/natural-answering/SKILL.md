# Natural Answering

## 왜 이 스킬이 있나

실제로 일어난 일이다. 20분짜리 분석을 끝내고 결과를 보고했더니 이런 답이 돌아왔다:

> 그래서 위의 결과가 뭔데???? 말을 너무 생략한 부분이 많아서 이해하기가 어려워

보고에 틀린 내용은 없었다. 숫자도 맞았고 표도 정확했다. 문제는 **읽는 사람이 알아야 하는
중간 단계를 전부 빼고 결론만 늘어놓은 것**이었다. 같은 내용을 생략 없이 다시 쓰자 바로 이해됐다.

빠진 것은 문법이 아니라 **설명의 사슬**이었다. 이 스킬은 그 사슬을 빼먹지 않게 하는 규칙이다.

## 생략하면 안 되는 여덟 가지

1~6은 위 사건에서, 7~8은 2026-11-11 작업 보고에서 실제로 빠졌던 것이다. "나쁨"이 처음 쓴 것,
"좋음"이 다시 쓴 것이다.

### 1. 용어의 뜻 — 처음 나오는 자리에서

```
나쁨: cross-mapping 위험은 낮습니다. 서로 다른 종 locus 294쌍 중 최장 완전일치가 34bp입니다.
좋음: 한 종의 DNA 조각을 다른 종의 것으로 착각할 위험(= cross-mapping)은 낮습니다.
      유전자 자리(= locus) 294쌍을 비교했더니, 글자가 하나도 안 틀리고 이어지는
      가장 긴 구간이 34글자였습니다.
```

`용어(= 쉬운 뜻 한 문장, 가능하면 비유)` 형태로 그 자리에서 푼다. 뒤에 모아서 설명하지 않는다 —
읽는 사람은 그 문장에서 이미 멈춘다.

### 2. 숫자에서 결론으로 가는 중간 단계

이것이 가장 많이 빠지고, 빠지면 가장 치명적이다. 숫자와 결론만 붙여 놓으면 읽는 사람은
**왜 그 숫자가 그 결론이 되는지** 알 수 없다.

```
나쁨: 최장 완전일치가 34bp입니다. 따라서 cross-mapping 위험은 낮습니다.
좋음: 기계는 DNA를 100글자씩 토막 내어 읽습니다. 그 토막이 엉뚱한 종에 붙으려면 100글자가
      다 맞아야 하는데, 두 종이 똑같은 구간은 최대 34글자뿐입니다. 나머지 66글자가 다르면
      프로그램이 버립니다. 그래서 위험이 낮습니다.
```

**검사법**: 결론 문장 앞에 "왜?"를 넣어 읽어 본다. 답이 글에 없으면 그 자리가 빈 것이다.

### 3. 비교 기준 — 그 숫자가 좋은 건지 나쁜 건지

```
나쁨: 완전일치 34bp.
좋음: 완전일치 34글자 — 토막 하나가 100글자이므로 그보다 훨씬 짧다(= 안전하다).
```

숫자 하나를 쓸 때마다 "무엇과 견주어 그런가"를 같은 문장이나 바로 다음 문장에 붙인다.

### 4. 문제 설정 — 무엇을 걱정해서 이걸 했는지

결과부터 시작하면 읽는 사람은 **그게 왜 중요한지 모르는 상태로** 숫자를 받는다.
한 문단으로 "이런 사고가 가능해서 그게 얼마나 일어나는지 재 봤다"를 먼저 그린다.

### 5. 주어 — 무엇이 그렇게 되는가

```
나쁨: 위키 밖 경로면 문자열 비교 몇 번으로 끝납니다.
좋음: 위키 밖 경로면 훅이 문자열 몇 개만 비교하고 바로 끝냅니다.

나쁨: 그마저 파일을 쓸 때만이다.
좋음: 그 비용도 파일을 쓸 때만 든다.
```

### 6. 단위를 일상어로

`bp → 글자`, `read → 토막`, `294쌍 → 294번의 비교`. 전문 단위를 그대로 두면 숫자의 크기가
읽는 사람에게 전달되지 않는다. 원래 단위가 필요하면 괄호로 같이 쓴다: `34글자(34bp)`.

### 7. 개수만 쓰지 않는다 — 항목을 쓴다

"N건"은 요약이지 보고가 아니다. 무엇인지 모르면 읽는 사람은 그대로 둬도 되는지 판단할 수 없다.
특히 **그대로 둔 것·확인 안 한 것**은 항목마다 무엇이고 무엇이 달라지는지를 쓴다.

```
나쁨: 리뷰가 알려 준 낮은 등급 지적 다섯 건은 그대로 두었습니다. 하나는 문자열 안의
      git commit 을 커밋으로 세는 것입니다. 나머지도 커밋 감지가 조금 넓거나 좁은 경우입니다.
좋음: 남은 4건 — 커밋이 아닌데 커밋으로 보는 경우(작업 보고를 괜히 한 번 더 쓰게 됨)
      1. 여러 줄 글을 쓰는 명령 안에 git commit 이라는 줄이 있을 때
      2. 화면에 글자를 찍는 명령 안에 있을 때. 예: echo 'a; git commit'
      남은 4건 — 커밋인데 못 보는 경우(그 턴의 작업 보고 검사를 건너뜀)
      3. 옵션을 띄어 쓴 커밋  4. 괄호로 묶은 커밋
```

개수를 쓸 때는 **센 다음에** 쓴다. 위 나쁜 예는 "다섯 건"이었지만 실제로는 리뷰가 든 6건 중
2건이 이미 고쳐져 4건이었다. 항목을 하나씩 적으면 개수가 틀릴 수가 없다.

### 8. 남이 쓴 말을 그대로 옮기지 않는다 — 풀어서 옮긴다

리뷰 에이전트·도구·로그가 쓴 말은 그것을 만든 쪽의 말이다. 그대로 옮기면 읽는 사람은 그
맥락이 없어서 무슨 뜻인지 모른다. 옮길 때는 세 가지를 붙인다: **무엇을 말하는지**,
**왜 중요한지(무엇이 달라지는지)**, **내가 확인했는지**.

```
나쁨: 리뷰가 확인하지 않은 범위도 있습니다. 위키 폴더 위치를 바꿨을 때의 제외,
      일부 편집 도구(NotebookEdit·MultiEdit) 전체 흐름입니다.
좋음: 위키 페이지만 고친 턴은 보고 대상에서 뺍니다. 위키 폴더를 기본 위치가 아닌 곳으로
      설정해도 빠지는지 리뷰어는 안 봤습니다. 다만 제 테스트가 다른 위치로 설정해서
      확인했고 통과합니다.
```

"리뷰어가 안 봤다"와 "아무도 안 봤다"는 다르다. 내가 테스트로 확인한 것이면 그렇다고 쓰고,
아무도 확인하지 않았으면 "확인이 아니라 추측"이라고 쓴다.

## 문장을 어색하게 만드는 것

| 쓰지 말 것 | 대신 |
|---|---|
| 이중 수동 — "생성되어진다" | "생성된다", 더 좋게는 "만든다" |
| 연결어미로 끝나는 문장 — "끝나므로." | 주절을 붙인다: "끝나므로 비용이 거의 없다." |
| 번역투 수동 — "훅에 의해 갱신된다" | 행위자를 주어로: "훅이 갱신한다" |
| 불필요한 사동 — "실행시킨다" | "실행한다" |
| 명사+하다로 늘리기 — "검사를 수행한다" | "검사한다" |
| 문장을 가리키는 말로 시작 — "이는 느리다" | 가리키는 것을 그 자리에 쓴다: "이 훅은 느리다" |
| 공문서투 — "해당 파일" | "그 파일" |

## 질문에 답했는지 확인한다

생략을 막고 짧게 써도, **질문에 답하지 않으면 아무 소용이 없다.**

2026-11-11에 이런 일이 있었다. 검사기가 코드에서 83건을 찾았고, 사용자가 물었다:
"뭐가 문제길래 고쳐야 해?" 세 번 물었고 세 번 다 답을 못 받았다.

```
물음:  왜 바꿔야 하는데? 뭐가 문제길래?

나쁨 1: "83건입니다 — 모호한 이름 51, 설명문 없음 22, 주석 없는 긴 함수 10."
        → 개수를 셌다. "왜" 를 묻는데 "얼마나" 를 답했다
나쁨 2: "세 종류로 갈립니다. 고칠 가치가 있는 것, 급하지 않은 것, 손해인 것."
        → 분류했다. 분류는 답이 아니라 답을 늦추는 방법이다
나쁨 3: "오늘 제가 당한 예가 있습니다. check_prose.py 에서 줄 단위로 재다가..."
        → 내 이야기를 했다. 사용자의 질문이 아니라 내 관심사다

좋음:  "고칠 필요 없습니다. 83건은 제 검사기가 과하게 잡은 것이고,
        그중 손해를 주는 것은 없습니다."
```

지키는 것 네 가지다.

1. **질문의 낱말로 먼저 답한다.** "왜"를 물으면 첫 문장이 이유여야 한다. "무엇을·얼마나·
   어떻게 나뉘는지"는 답이 아니다. 답한 뒤에 설명을 붙인다
2. **같은 질문이 두 번 오면 답을 안 한 것이다.** 그때 설명을 더 붙이면 더 멀어진다.
   앞 답을 버리고 한 문장으로 다시 답한다
3. **"아니다 / 없다 / 안 해도 된다"가 답일 수 있다.** 할 일을 제안하는 것이 진전처럼
   보여서 답을 미루게 되는데, 사용자가 물은 것은 할 일이 아니라 답이다
4. **모르면 "모른다"가 답이다.** 주변 설명으로 빈칸을 채우지 않는다

이 확인은 기계가 절반만 할 수 있다. `hooks/py/answer-check.py` 가 **같은 질문이 다시
왔는지**는 보지만, 답이 질문에 닿았는지는 못 본다.

훅은 한 번만 요청한 것과, 답이 빗나가서 다시 요청한 것을 이렇게 가른다.

- 사람이 직접 쓴 메시지만 센다. 대화 요약문·규칙 묶음·훅 피드백·도구 결과는 기록에서
  user 자리에 있어도 사람 말이 아니다
- 두 메시지 사이에 답이 있어야 한다. 답을 받기 전의 재전송은 되물음이 아니다
- 근거는 둘 중 하나다. 되묻는 말투(`data/reask-markers.txt`: "모르겠다니까", "아니....")가
  있거나, 앞 질문과 거의 같은 질문을 또 보냈거나다. **의문사('왜', '무엇')가 겹치는 것은
  근거가 아니다** — 새 질문에도 늘 들어간다
- 연달아 되물으면 몇 번째인지 센다. 3번째라면 앞의 두 답이 다 빗나간 것이다 그건 답을 쓴 뒤 **질문을 다시 읽고**
첫 문장이 그 질문의 답인지 보는 것으로만 확인된다.

## 짧게, 한 번만

생략을 막다 보면 반대쪽으로 넘어간다. 오늘 이 스킬을 만들면서 제가 쓴 보고가 그랬다 —
40줄이 넘고 표가 세 개씩 들어갔다. 결론은 맨 앞에 있었지만, 읽는 사람은 **어디까지가
중요한지 알기 위해 전체를 훑어야** 했다. 생략이 없는 것과 읽기 쉬운 것은 다르다.

1. **답변은 화면 하나 안에서 끝낸다** — 25줄 안팎. 그보다 길어지면 그건 답변이 아니라
   문서다. 문서로 만들고 **요약 세 줄 + 경로**를 준다
2. **표는 둘 이상을 같은 기준으로 견줄 때만 쓴다.** 한 답변에 표가 세 개면 이야기를 표로
   쪼갠 것이다. 표의 칸에는 값이 들어가고, 이유는 문장으로 쓴다
3. **같은 말을 두 번 쓰지 않는다.** 맨 앞에 쓴 결론을 아래 절에서 다시 설명하지 않는다
4. **질문에는 보고 형식을 쓰지 않는다.** 작업 보고 여섯 단계는 **일을 끝낸 뒤**에만 쓴다.
   질문에는 답 한 단락이면 된다
5. **용어 설명이 문장 가운데를 두 겹으로 만들면 따로 뺀다.** 괄호 안에 설명이 한 줄을
   넘어가면 다음 문장으로 내린다
6. **백틱과 볼드를 아낀다.** 한 문단에 백틱이 여섯 개를 넘으면 글이 아니라 목록이다

```
나쁨: 훅(= 특정 사건이 일어날 때 하네스가 대신 돌려 주는 작은 프로그램)이 `PostToolUse`
      에서 `Write`·`Edit` 에만 걸려 있어서 `Bash` 로 쓰면 `wiki-graph` 가 안 돈다.
좋음: 훅은 파일을 쓸 때 자동으로 도는 작은 프로그램이다. 지금은 Write와 Edit에만
      걸려 있어서, 쉘로 파일을 쓰면 그래프 갱신이 건너뛰어진다.
```

## 글의 뼈대 (보고·분석 결과)

위 사건에서 통했던 순서다. 결과가 여러 개면 **결과마다** 2·3번을 반복한다.

1. **무엇을 걱정했나** — 그림 하나를 그려 준다
2. **어떻게 쟀나** — 데이터가 무엇이고 한 줄이 무엇인지
3. **결과 N** — 숫자 → 그 숫자가 왜 그 뜻인지 → 그래서 무엇이 달라지는지
4. **내가 틀린 것** — 중간에 방법을 바꿨으면 왜 바꿨는지 숨기지 않는다
5. **아직 모르는 것** — 가장 큰 빈칸 하나. 결론의 범위를 좁혀서 말한다
   ("위험이 낮다"가 아니라 "비교한 유전자 7개 사이에서는 낮다")

표를 쓸 때는 **표 앞에 길잡이 한 줄**을 둔다 — "아래 표는 무엇과 무엇을 견준 것이다".
표만 던지면 읽는 사람이 어느 칸을 봐야 하는지 모른다.

## 작업 보고 — 코드를 고친 뒤

여섯 단계 순서로 쓴다: **작업 결과 → 작업 요약 → 변경사항 → 검증 결과 → 문제 및 제약 →
후속 조치.** 고친 과정과 자기평가를 늘어놓지 않는다. 읽는 사람이 알아야 할 것이 매번 같은
자리에 오게 한다. 세 가지만 지키면 나머지는 따라온다:

- "완료 / 부분 완료 / 실패"를 맨 앞 한 단어로 먼저 밝힌다
- 검증은 숫자로 쓴다 — "테스트 통과"가 아니라 "단위 테스트 12/12 통과"
- "문제 및 제약"을 비우지 않는다. 검증하지 않은 항목은 거의 항상 있다

전체 표와 예시는 `references/work-report.md` 를 읽는다.

**훅이 검사한다.** 사용자 파일을 고쳤거나 커밋한 턴은, 마지막 답변에 여섯 항목이 그 표의
이름과 순서로 있어야 한다. 1번 바로 뒤에는 결과 낱말이 와야 한다. 빠지면 `answer-check` 가 한 번
막는다. 위키 페이지만 쓴 턴, 임시 폴더만 쓴 턴, 쓰고 지운 파일은 세지 않는다. Bash 로 파일을
고친 것은 훅이 못 본다 — 그때도 같은 틀로 보고한다.

## 문서 구조 — 위키가 아닌 문서

README·Architecture·API Reference 처럼 `~/llm-wiki-docs/` 밖에 만드는 문서는, 모든 문서에
같은 목차를 강제하지 않는다. **종류를 먼저 판별하고 그 종류의 뼈대를 쓴다.** 공통 10항목,
문서 종류별 구조, 쓸 때 지키는 일곱 가지는 `references/document-structure.md` 에 있다.

코드와 관련된 문서에서 가장 흔한 사고는 **없는 API나 돌려 보지 않은 명령어가 문서에 들어가는
것**이다. 명령어·경로·파라미터는 실제 구현과 대조한다(`source-of-truth.md`).
위키 페이지는 이 뼈대가 아니라 `llm-wiki-docs` 스킬의 규약을 따른다.

## 기계로 먼저 걸러내기

```bash
scripts/check_prose.py <파일...>        # 경고만
scripts/check_prose.py --all <파일...>  # 참고 등급까지
```

잡는 것:

- 뜻 없이 쓴 약어와 영문 용어
- 비교 기준 없는 숫자
- 90자 넘는 문장 (한글이 없는 문장은 180자)
- 연결어미로 끝나 주절이 빠진 문장
- 주어가 빠진 듯한 문장
- 비교 대상 없는 "더 ~", 개수 없는 "전부"
- 길잡이 문장 없이 바로 나오는 표
- 한 문단에 볼드 네 개 이상
- 이중 수동·번역투·공문서투
- 문서에 적혀 있지만 실제로 없는 파일 경로

판정 기준은 전부 `data/` 에 있다 — 패턴은 `patterns.tsv`, 설명 없이 써도 되는 약어와 영문
낱말은 `known-acronyms.txt`·`known-terms.txt`, 비교로 인정하는 말은 `baseline-words.txt`.
도메인 용어가 계속 걸리는데 그 분야에서 상식이라면 그 파일에 한 줄 추가한다. 코드를 고치지 않는다.

**스크립트가 조용한 것이 잘 썼다는 뜻은 아니다.** 1번·2번·4번(용어의 뜻, 중간 단계, 문제 설정)은
기계가 못 본다. 스크립트는 빠진 자리를 가리킬 뿐이고, 사슬이 이어졌는지는 직접 읽어서 확인한다.

## 자동 검사

`hooks/py/prose-check.py` 가 PostToolUse 로 돈다. 위키 페이지(`<루트>/<주제>/wiki/**/*.md`)를
쓰면 경고만 뽑아서 보여주고, 그 밖의 파일이면 즉시 끝낸다. 막지 않는다 — 글은 기계가 판정할
대상이 아니라서, 경고는 다시 읽어 볼 자리를 알려 주는 것까지다.
